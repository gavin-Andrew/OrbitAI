## 1. 本阶段目标

V4.0 已经建立第一版产业世界模型和 SQLite 迁移基线。V4.1 不再继续扩展概念模型，而是建立一套可浏览、可纠错、可重复导入的产业与参与者名册，为后续事件识别提供稳定身份坐标。

本阶段需要跑通：

```text
人工智能产业
-> 核心能力、基础设施、产品与应用、外部环境
-> 四大分组下的 26 个赛道
-> 唯一深度试点：通用基础模型（含大语言模型）
-> 组织与人物稳定身份
-> 别名、任职和赛道关系
-> 来源身份与获取入口映射
-> 浏览、预览冲突和人工纠错
```

V4.1 的完成标准不是收录尽可能多的企业和人物，而是让后续系统读到不同语言、缩写和历史称呼时，能够优先关联已有身份，不重复创建对象。

## 2. 已确认范围

### 2.1 内容范围

- 顶层产业为“人工智能产业”。
- V4 全阶段唯一深度试点为“通用基础模型（含大语言模型）”。
- 核心能力、基础设施、产品与应用、外部环境四大分组是“人工智能产业”和 26 个赛道之间不可省略的正式目录层级，不只是页面颜色、标签或临时排序。
- 第一版 AI 产业目录由四大分组和 26 个已确认赛道共同构成；除试点外，其余赛道只标记为 `directory_only`，不建设参与者、事件、来源证据和档案内容。
- 仓储、导入、路由和页面能力必须保持赛道通用，不得把试点 ID 硬编码为系统唯一赛道。

四大分组与赛道数量固定为：

| `segment_kind` | 显示名称 | 赛道数 | V4.1 内容状态 |
|---|---|---:|---|
| `core_capability` | 核心能力 | 5 | 包含唯一深度试点 |
| `infrastructure` | 基础设施 | 6 | 仅目录骨架 |
| `product_application` | 产品与应用 | 8 | 仅目录骨架 |
| `external_environment` | 外部环境 | 7 | 仅目录骨架 |

现有 `segments.segment_kind` 继续作为数据库中的分组字段。V4.1 不为四大分组另建复杂分类树；种子使用 `segment_groups` 明确保存显示名称、顺序和说明，页面按 `segment_kind` 分组查询和渲染。

### 2.4 首个页面的已确认层级

V4.1 首个页面正式选择产业/赛道总览，而不是事件台账。页面必须保持以下信息层级：

```text
人工智能产业
-> 核心能力
   -> 5 个赛道，其中“通用基础模型”高亮并可继续下钻
-> 基础设施
   -> 6 个待建设赛道
-> 产品与应用
   -> 8 个待建设赛道
-> 外部环境
   -> 7 个待建设赛道
```

页面可以使用四个分组卡片、分栏或其他适合服务端渲染的布局，不要求复刻复杂思维导图交互；但不能把 26 个赛道直接铺成一个无分组列表，也不能因为只有一个试点而隐藏另外三大类。

### 2.5 本阶段不做

- 不创建真实事件、事件时间线、主张或观点。
- 不把现有文章自动回填为文档或事件。
- 不由 AI 自动创建组织、人物或别名。
- 不自动合并名称相似但身份边界不清的组织。
- 不把种子数据放进数据库迁移并在初始化时静默写入。
- 不为目录骨架中的其他赛道生成介绍性内容。
- 不改造静态快照；名册整理工作流只进入本地动态 Web App。

## 3. 名册对象与现有数据表

V4.0 已经提供 V4.1 所需的主要物理表。V4.1 优先复用这些表：

| 名册对象 | 物理表 | V4.1 用途 |
|---|---|---|
| 产业 | `industries` | 保存人工智能产业稳定身份 |
| 赛道 | `segments`、`industry_segments` | 保存完整目录骨架和试点赛道 |
| 组织 | `organizations`、`organization_aliases` | 保存规范名称、别名和组织边界 |
| 人物 | `people`、`person_aliases` | 保存人物规范名称和别名 |
| 任职 | `person_organization_roles` | 保存人物与组织的带时间关系 |
| 赛道参与 | `organization_segments`、`person_segments` | 将首批参与者关联到试点赛道 |
| 来源身份 | `sources` | 将长期追踪来源映射到组织或人物 |
| 获取入口 | `source_entries` | 保存 RSS、官网和手动录入入口 |

种子文件中的以下字段属于策划和导入元数据，不应在没有明确迁移设计时强行塞入现有业务表：

- `content_status`
- `verification_status`
- `verification_source_ids`
- `registry_action`
- `mapping_status`

导入器应使用这些字段生成预览与冲突报告；正式写库时，只写入已经有明确表字段和已经通过复核的内容。

## 4. 稳定身份与别名规则

### 4.1 稳定 ID

- ID 创建后不随显示名称变化。
- ID 使用小写英文和下划线，不直接使用页面标题生成永久身份。
- 组织、人物和来源处在不同命名空间，可以共享可读 ID，但导入报告必须同时显示对象类型。

### 4.2 名称规范化

导入预览至少执行：

- Unicode NFKC 规范化。
- 去除首尾空格并折叠连续空格。
- 英文大小写归一后比较。
- 同时检查规范名称和全部别名。
- 零个匹配时列为 `create`。
- 一个匹配时列为 `map_existing` 或 `update_preview`。
- 多个匹配时列为 `conflict`，禁止自动选择。

显示名称仍保留原始大小写、语言和标点，不能把规范化后的检索键直接展示给用户。

### 4.3 组织边界

- OpenAI、Anthropic 先以品牌和研究组织层级建档，V4.1 不拆分内部法律实体。
- Google DeepMind 是本次参与者身份；现有来源注册表中的 `Google DeepMind / Google AI` 拆成两个来源身份。`google_deepmind` 映射参与者，`google_ai` 暂时不绑定参与者，不能把 `Google AI` 保存为 Google DeepMind 的普通别名。
- Meta AI 先作为 Meta 内部 AI 研究与产品组织建档，不等同于 Meta Platforms 整个公司。
- DeepSeek 先按品牌和研究团队层级建档；官网涉及多个关联法律实体，V4.1 不把它们未经审核地全部合并成别名。
- SpaceXAI 采用项目已经确认的当前主名称，保留 `xAI`、`xAI Corp.` 作为历史检索别名；其与历史 xAI、SpaceX 的组织变化在 V4.2 作为事件处理，不在 V4.1 用别名关系代替历史事件。

## 5. 任职关系规则

- `role_title` 保存来源实际支持的身份，不根据知名度推断职务。
- 官网只证明当前职务、没有给出上任日期时，`started_on` 保持空字符串。
- 只可靠到年份或月份时，分别保存 `YYYY` 或 `YYYY-MM`，不补虚构日期。
- `ended_on` 没有可靠信息时保持 `null`。
- `is_current` 只在来源能够支持当前关系时设为 `1`。
- 官方来源优先；只有可靠二手来源时标记为 `secondary_verified`，后续仍需要补一手来源。
- 人物是组织创始人，不自动意味着其仍担任 CEO 或其他当前职务。

## 6. 来源注册表映射

`sources.v4.json` 是来源注册表，不是参与者名册。V4.1 的映射遵循：

- 来源身份可以映射一个组织或一个人物，但不能同时映射两者。
- RSS、官网、访谈和手动录入只是 `source_entries`，不能替代 `sources`。
- 现有来源注册表 ID 能复用时保持不变。
- 新增来源先标记 `registry_action=propose_create`，在导入预览中单独列出。
- 旧字段 `industries` 使用的是此前宽泛产业方向 ID，不允许直接映射为“通用基础模型”赛道。
- `related_source_ids` 只作为策划线索；人物与组织的正式关系写入 `person_organization_roles`。

当前 12 个参与者对应 12 个核心来源；拆分后另保留 1 个范围更宽的 Google AI 补充来源，因此种子共有 13 个来源身份：

| 类别 | 来源 ID | 处理方式 |
|---|---|---|
| 复用现有组织源 | `openai`、`anthropic`、`meta_ai`、`spacexai` | 映射已有参与者 |
| 拆分现有组合源 | `google_deepmind_google_ai` -> `google_deepmind`、`google_ai` | 前者映射参与者，后者有意暂不绑定 |
| 新增组织源草案 | `deepseek` | 提议创建 |
| 复用现有人物源 | `sam_altman`、`dario_amodei`、`elon_musk` | 映射已有来源 |
| 新增人物源草案 | `demis_hassabis`、`yann_lecun`、`liang_wenfeng` | 提议创建 |

拆分操作必须在导入预览中单独显示，旧组合来源不能与两个新来源并存为三个活动来源。`google_ai` 使用 `mapping_status=intentionally_unbound`，表示暂不绑定是已确认决定，不是遗漏或冲突。

## 7. 种子文件规则

`data/catalog/foundation_models.v4.1.json` 是可审核的策划输入，不是数据库真相。它应满足：

- 明确标记 `status=draft`。
- 显式保存 4 条 `segment_groups`，并保证 26 个赛道全部使用其中一个 `segment_kind`。
- 保留已经确认的范围和仍待复核的字段。
- 每个对象使用稳定 ID。
- 所有外键式引用都必须指向同一文件中的现有 ID。
- 核查来源使用独立 `verification_sources` 列表，业务对象只保存来源 ID。
- 未通过复核的映射不能在后续 `apply` 模式中写库。
- 重复导入必须幂等，不新增重复别名、任职或来源入口。

### V4.1-B：导入预览（已实现）

- 读取种子和 `sources.v4.json`。
- 输出 `create`、`create_from_split`、`map_existing`、`intentionally_unbound`、`unchanged`、`update_preview`、`conflict` 和 `blocked`。

- 导入失败时整批回滚，不留下半套名册。

```powershell

python -m orbitai.catalog_import apply --confirm-seed-id v4_1_foundation_models_roster --summary-only
```

## 9. V4.1 验收标准

- AI 产业的目录骨架包含且只包含 4 个正式分组，顺序为核心能力、基础设施、产品与应用、外部环境。
- 四大分组分别包含 5、6、8、7 个赛道，总数为 26；任何赛道都不能绕过分组直接出现在产业根节点下。
- 只有“通用基础模型（含大语言模型）”标记为 `pilot_active`。
- 首批恰好包含 6 个组织和 6 位人物。
- 每个参与者都关联试点赛道。
- 规范名称、别名和稳定 ID 可以区分。
- 6 条人物—组织关系均带核查状态，不确定日期没有被补成精确日期。
- 12 个参与者均有一个核心来源，另有一个有意暂不绑定的 Google AI 补充来源，共 13 个来源身份。
- `Google DeepMind / Google AI` 拆分操作可预览，旧组合来源不会被静默保留为活动来源。
- 导入预览不写数据库，重复应用不产生重复数据。
- 用户修改后的数据不会被后续导入静默覆盖。
- 能从“人工智能产业”依次经过四大分组、试点赛道，浏览到组织、人物和来源入口。
- Python 编译、迁移测试、名册仓储测试、导入幂等测试和关键路由测试通过。
