# OrbitAI V4.1-D 名册最小管理入口说明

类别：操作与实现指南

状态：最小人工纠错闭环已实现。

版本：2026-07-18

## 1. 这一块解决什么问题

V4.1-A/B/C 完成后，我们已经能够：

```text
把审核过的种子写入数据库
-> 从数据库读取产业、组织和人物
-> 在产业档案阅读端展示
```

但是，真实资料会不断变化，也可能发现早期录入有误。如果只能重新修改种子并导入，日常纠错会很笨重；如果直接用数据库工具修改，又容易覆盖他人刚保存的内容，也不会留下“为什么改”的记录。

V4.1-D 因此补上：

```text
独立管理入口
-> 修改前预览
-> 冲突检测
-> 事务保存
-> 修改记录
```

管理地址：

```text
http://127.0.0.1:8000/admin/catalog
```

## 2. 当前“最小”管理范围

当前可以编辑组织和人物的：

- 规范名称。
- 简介。
- 状态，包括使用“已归档”代替物理删除。
- 别名，可以增加或移除。
- 组织类型和组织官网。

当前没有开放：

- 人物任职关系。
- 组织和人物的赛道关系。
- 来源映射。

这些关系会同时影响多个档案，误改的后果更大。V4.1 最小入口先验证安全编辑机制；关系数据继续通过已审核的种子、导入预览和后续专门关系编辑器维护。

## 3. 页面为什么独立

产业档案阅读端面向“阅读研究结果”，管理入口面向“修改数据库”。两者目的不同：

| 阅读端 | 管理端 |
|---|---|
| 默认展示已确认内容 | 明确提醒正在修改数据 |
| 不提供保存按钮 | 必须先预览再保存 |
| 使用 `templates/dossier/` | 使用 `templates/admin/catalog_editor.html` |
| 使用 `static/dossier/` | 使用独立的管理 CSS 和 JavaScript |

独立并不是指建立第二套数据库。两个页面仍读取同一个 `var/orbitai.db`，只是入口、操作权限和视觉提示分开。

## 4. 一次修改的完整流程

假设用户准备修改 OpenAI 的简介：

```text
1. 打开管理页
   系统读取 OpenAI 当前内容，并计算版本指纹

2. 修改表单
   此时只改了浏览器中的草稿，数据库没有变化

3. 点击“预览修改”
   后端重新读取数据库、检查版本、名称冲突和字段格式
   返回“修改前 / 修改后”差异

4. 填写修改原因
   例如：根据官网 About 页面更新组织简介

5. 点击“确认并保存”
   后端再次检查冲突
   在一个事务中更新名册和写入修改记录

6. 保存成功
   阅读端下次刷新时读取到新内容
```

为什么保存前要检查两次？因为用户看完预览到点击保存之间，数据库仍可能被另一个页面修改。第二次检查可以关闭这段时间窗口。

## 5. 什么是版本指纹

系统把一个对象当前可编辑的内容整理成稳定 JSON，再计算 SHA-256 摘要。例如：

```text
名称 + 简介 + 状态 + 官网 + 组织类型 + 别名 + updated_at
                         ↓
                  一串固定长度指纹
```

页面打开时保存旧指纹。预览和保存时，后端都重新计算当前指纹：

```text
旧指纹 = 当前指纹  -> 可以继续
旧指纹 ≠ 当前指纹  -> HTTP 409 冲突，拒绝覆盖
```

这叫“乐观并发控制”。“乐观”不是盲目信任，而是假设大多数时候不会同时编辑；真正保存时再用指纹严格确认。

## 6. 冲突检测有两类

### 6.1 并发冲突

小张和小李同时打开 OpenAI：

1. 小张先保存，新版本进入数据库。
2. 小李的页面仍拿着旧指纹。
3. 小李保存时收到 409 冲突。
4. 小李必须刷新、阅读小张的新内容，再决定怎样修改。

系统不会使用“最后点保存的人自动获胜”，因为那会静默丢失小张的修改。

### 6.2 身份名称冲突

规范名称和别名都属于身份检索空间。系统使用与种子导入相同的 Unicode 规范化规则，因此：

```text
OpenAI
 openai
ＯｐｅｎＡＩ
```

会被视为同一个检索身份。不能把其中一个形式作为 Anthropic 的别名，否则后续材料无法可靠判断它指向谁。

## 7. 什么是事务保存

一次保存至少涉及两类数据：

```text
业务表：organizations / people / aliases
审计表：catalog_change_log
```

SQLite 事务保证：

```text
业务修改成功 + 修改记录成功 -> 一起提交
任何一步失败                 -> 全部回滚
```

例如，简介已经更新，但修改记录因为磁盘错误无法写入，系统不会保留那份简介。否则数据库里会出现“内容变了，但不知道谁为什么改”的断裂状态。

保存使用 `BEGIN IMMEDIATE`。它会在检查当前版本和写入之间取得写锁，避免另一个写操作插进同一个关键区间。

## 8. 修改记录保存什么

新增迁移 `0006 catalog_change_log_v1`，建立 `catalog_change_log` 表。每次成功修改记录：

- 对象类型和稳定 ID。
- 操作类型：更新、归档或恢复。
- 哪些字段发生变化。
- 修改前完整快照。
- 修改后完整快照。
- 用户填写的修改原因。
- 保存前版本和保存后版本。
- 操作者，目前固定为本地用户。
- 保存时间。

审计表没有使用指向组织或人物的级联删除外键。即使业务对象以后归档，历史修改记录仍会保留。

## 9. 代码怎样分工

### 数据库迁移

文件：`orbitai/core/migrations.py`

建立修改记录表和查询索引。数据库结构变化通过正式迁移管理，没有把临时 `ALTER TABLE` 堆进初始化函数。

### 仓储层

文件：`orbitai/catalog/repository.py`

负责读取可编辑对象、更新允许字段、整体替换别名、写入和读取修改记录。它只接受白名单字段，不能由网页随意传入 SQL 字段名。

### 编辑服务

文件：`orbitai/catalog/edit_service.py`

负责字段校验、身份冲突、版本指纹、差异预览、事务和操作类型判断。真正的安全规则集中在后端，不能只依靠浏览器按钮。

### 路由

文件：`orbitai/web/routes/admin.py`

新增：

```text
GET  /admin/catalog
POST /admin/catalog/preview
POST /admin/catalog/save
```

验证错误返回 HTTP 422，并发冲突返回 HTTP 409，不存在的对象返回 HTTP 404。页面可以根据状态码给出不同提示。

### 模板和前端

文件：

- `templates/admin/catalog_editor.html`
- `static/admin/catalog.css`
- `static/admin/catalog_editor.js`

JavaScript 负责表单交互和展示差异，但保存接口会在后端重新执行全部校验。因此即使有人绕过页面直接请求接口，也不能绕过冲突检查。

## 10. 与种子文件是什么关系

管理页修改的是当前活动数据库，不会反向修改 `data/seeds/catalog/foundation_models.v4.1.json`。

这是有意设计：

- 种子是经过审核的初始策划输入。
- 数据库是运行过程中持续维护的当前状态。
- 再次运行导入预览时，人工修改会显示为差异或冲突。
- 导入器不会静默覆盖用户通过管理页保存的内容。

如果未来确认某项修改也应成为新环境的默认种子，需要单独审核并更新种子，而不是由网页悄悄同步。

## 11. 怎样验证

聚焦测试：

```powershell
python -m unittest tests.catalog.test_catalog_edit -v
```

测试覆盖：

- 预览不写数据库。
- 正常保存同时产生修改记录。
- 旧版本不能覆盖新版本。
- 规范化名称和别名冲突被拒绝。
- 修改记录写入失败时，业务数据和别名全部回滚。
- 归档操作被正确记录为 `archive`。
- 管理页面与预览/保存路由返回正确状态码。

完整测试：

```powershell
python -m unittest discover -s tests -v
```

本轮最重要的验收并不是页面按钮能否点击，而是证明“冲突时不覆盖、失败时不留半套数据、成功时一定有修改记录”。
