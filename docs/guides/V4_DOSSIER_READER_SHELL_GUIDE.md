# OrbitAI V4 产业档案阅读端模板骨架说明

类别：操作与实现指南

状态：V4.1-C 阅读端骨架已实现；当前布局是可以继续迭代的产品骨架，不是最终视觉定稿。

版本：2026-07-18

## 1. 用一句话解释这次做了什么

我们把产业档案从原来的“信息流页面加一个产业目录”改成了一套独立的阅读端，并固定三个一级入口：

```text
产业结构    企业档案    人物档案
```

这三个入口共用同一个页头、导航、页面宽度和页脚。今后新增赛道、企业、人物、事件和时间线时，都装进这套骨架，不需要每次重新设计整张网页。

## 2. 我们原来有什么，现在又有什么

### 2.1 原来已经有的后台能力

- `var/orbitai.db` 中已经有四大类、26 个赛道、6 个组织和 6 位人物。
- 仓储层可以从 SQLite 读取产业和试点参与者。
- `/industries/artificial-intelligence` 已经证明“数据库数据能够显示到浏览器”。
- RSS 材料库和管理页面已经按自己的模板与 CSS 独立保留。

原来的产业页更像一张工程检查单：它证明货物确实从仓库搬到了网页，但不是用户以后长期使用的“产业档案书架”。

### 2.2 这次新增的阅读端

| 页面 | 地址 | 当前作用 |
|---|---|---|
| 产业结构 | `/industries/artificial-intelligence` | 展示四大类与 26 个赛道，是默认入口 |
| 企业档案 | `/organizations` | 展示首批 6 个真实组织 |
| 人物档案 | `/people` | 展示首批 6 位人物及当前任职关系 |
| 赛道档案骨架 | `/segments/general-foundation-models` | 承接产业结构中的试点赛道跳转 |

赛道页不属于第四个一级入口。它是从“产业结构”继续向下阅读的二级页面。

## 3. 为什么叫“模板骨架”

可以把网页想成一本书：

- 模板骨架是书的开本、目录栏、页眉、正文区域和页脚。
- 数据库内容是每一页真正写了什么。
- CSS 是字体、颜色、间距和版式。
- 路由是目录页中的页码，决定一个网址应打开哪一页。

骨架稳定以后，可以继续调整颜色或版式，也可以往正文区增加事件时间线，而不用改动三个一级入口和数据读取关系。这就是为什么现在先固定信息架构，而不一次性把所有视觉细节和未来功能做完。

## 4. 用户打开页面时，数据怎样流动

```text
用户点击“人物档案”
        ↓
FastAPI 路由识别网址 /people
        ↓
服务层提出需求：需要人物、别名和当前任职
        ↓
仓储层向 SQLite 分别查询这些表
        ↓
服务层把分散的关系组装到每个人物下面
        ↓
Jinja2 把真实数据填入人物页面模板
        ↓
CSS 把 HTML 排成用户看到的档案卡片
```

这里的逻辑分层很重要。SQL 只负责正确取数，Jinja2 只负责生成 HTML，CSS 只负责外观。以后只重画页面时，不会连带破坏数据库代码。

## 5. 具体改了哪些代码，为什么

### 5.1 仓储层：增加通用读取方法

文件：`orbitai/catalog/repository.py`

新增读取赛道、组织、组织别名、人物、人物别名和当前任职的方法。仓储层集中保存 SQL，可以理解为数据库的“统一窗口”。页面不直接接触数据表，能减少同一种查询在多个页面里重复出现。

这些查询只读，不会修改正式数据库。

### 5.2 服务层：把关系整理成页面容易使用的形状

文件：`orbitai/catalog/service.py`

SQLite 中的人物、别名和任职关系位于不同数据表。服务层把它们整理成类似下面的页面数据：

```text
Sam Altman
├─ 别名：……
├─ 当前组织：OpenAI
└─ 当前角色：……
```

服务层还把组织类型代码转换成中文显示名称，并根据真实参与者关系判断一个赛道是否已经建设。它没有把试点 ID 写死，因此未来另一个赛道有了名册，也能使用同一套代码。

### 5.3 路由：固定阅读路径

文件：`orbitai/web/routes/dossier.py`

路由负责把网址、服务和模板接起来。三个一级地址已经固定，试点赛道使用通用的 `/segments/{segment_slug}` 规则。

`slug` 是网址使用的稳定英文名称。例如 `general-foundation-models` 指向“通用基础模型（含大语言模型）”。中文标题可以调整，而网址身份仍能保持稳定。

### 5.4 Jinja2：建立共用外壳和四张内容模板

目录：`templates/dossier/`

- `base.html`：共用品牌、三个入口和页脚。
- `industry_structure.html`：四大类与 26 个赛道。
- `organization_directory.html`：企业与机构名册。
- `person_directory.html`：人物与任职名册。
- `segment_profile.html`：赛道介绍、参与者和未来时间线位置。

“模板继承”是指四张内容页都复用 `base.html`。如果以后修改顶部三个入口，只改一次基础模板即可，不必在每张页面复制修改。

### 5.5 CSS：把产业阅读端与旧材料端隔开

文件：`static/dossier/style.css`

产业档案使用自己的 `dossier-` 样式命名空间，RSS 材料页继续使用 `static/materials/`，管理页继续使用 `static/admin/`。这样重设计产业档案时，较难误伤仍有保留价值的材料抓取与管理功能。

当前 CSS 已经支持桌面双侧产业结构和手机单列布局。它是第一版视觉骨架，后续可以继续做用户体验调整。

## 6. 为什么时间线现在是空的

赛道页已经预留“赛道发展历程”和“企业发展时间线”，但明确显示等待 V4.2 事件台账。

原因是时间线不是装饰。一个节点至少要有事件时间、参与者和原始来源，之后用户还要能点击进入事件档案。V4.1 目前只有名册，没有经过审核的事件；现在自动生成一段历史，会把“看起来合理的文字”错误地伪装成“可追溯事实”。

因此当前页面诚实展示空位，等事件数据模型和审核流程完成后再填充。

## 7. 这次没有做什么

- 没有创建企业或人物独立详情页；当前完成的是两个总入口。
- 没有增加搜索、筛选和分页，因为首批各只有 6 条。
- 没有编写或生成赛道发展史。
- 没有创建企业时间线和事件档案。
- 没有删除 RSS 材料库、管理页或旧数据。
- 没有改动数据库结构，也没有再次写入种子。

## 8. 怎样查看和验证

启动本地应用：

```powershell
uvicorn app:app --reload
```

浏览器打开：

```text
http://127.0.0.1:8000/industries/artificial-intelligence
```

运行本轮聚焦测试：

```powershell
python -m unittest tests.catalog.test_catalog_page tests.acceptance.test_web_structure -v
```

测试会检查固定入口、四大类、26 个赛道、6 个组织、6 位人物、试点跳转、未知地址的 404，以及材料端与产业端的静态资源边界。

## 9. 以后添加功能时怎样复用

后续 V4.2 建立事件后，主要是在服务层增加事件数据，并在 `segment_profile.html` 的两个时间线区域渲染；顶部三个入口不变。以后新增企业详情页或人物详情页，也是在现有总入口下增加二级路由，不必推翻阅读端基础模板。

这就是本轮骨架的实际价值：先固定“用户从哪里进入、沿什么路径阅读”，再逐步填充可核查内容。
