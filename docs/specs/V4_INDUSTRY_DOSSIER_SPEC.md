# OrbitAI V4 动态产业档案实现规格

类别：实现规格

状态：实现草案，含已确认规则与已实现基线。V4.0 产业范围、事件规则、对象关系和 V4 单赛道约束已经用户确认；2026-09-13 用户进一步确认从 V4.2 首批事件开始交付人工整理闭环、提前记录研究线索并以实际使用和整理成本验收。该确认不覆盖尚待策划的首批事件、具体新增字段或数据写入；其余未确认内容仍为草案。总体方向以 `docs/product/ORBITAI_ROADMAP.md` 为准。

版本：2026-09-26。V4.2 剩余功能已工程交付并通过用户统一验收（核心功能无明显问题），当前范围见 `V4_2_COMPLETION_SPEC.md`，结果见 `../guides/V4_2_ACCEPTANCE.md`。`V4_2_EVENT_SLICE_SPEC.md` 保留首批未确认样本写入记录；旧阶段基线不代表当前缺失能力。

## 1. 本规格解决什么

本规格记录 V4.0 已建立的数据基线，并约束后续 V4 切片怎样把它转化为可用的研究流程。它不尝试一次设计完 V4 的全部页面、AI 工作流和长期分析对象，核心数据路径是：

```text
产业
-> 细分赛道
-> 企业/机构/人物
-> 关键事件
-> 来源身份与原始文档
```

V4.0 已通过迁移建立这条路径所需的基础表，包括 `events`、`documents` 和 `event_documents`；V4.1 名册、阅读端骨架和最小纠错入口也已实现。下一切片是复用现有表完成 V4.2 的事件整理与展示流程，不能把基础表存在当作流程已完成，也不从重复建表开始。第 4、7.1 节保留 V4.0 切片边界和验收基线。

## 2. 已确认规则与当前假设

### 2.1 已经确认

- 第一版顶层产业为“人工智能产业”。
- AI 产业第一版分为核心能力、基础设施、产品与应用、外部环境四大部分；它们之间允许存在支持、依赖、供应、采用、竞争、合作和监管等关系，不强制表达为单一分类树。
- 第一个深度试点赛道正式选择“通用基础模型（含大语言模型）”。
- V4.1 至 V4.5 先只在该试点赛道建设参与者、事件、来源证据、档案内容和整理闭环；达到 V4 退出标准后，再横向补充其他赛道内容。
- 单赛道限制只适用于当前内容范围。已经确认的产业目录骨架可以保留，未建设赛道必须明确显示为空白或待建设；数据模型、仓储、导入、路由和页面仍须保持赛道通用，不得把试点硬编码为唯一业务对象。
- V4.1 首批名册正式采用 6 个组织和 6 位人物的范围，已于 2026-07-16 完成首次审核与写入；具体名单、身份边界和种子字段见 `docs/specs/V4_1_CATALOG_SPEC.md`。本轮不扩充名单；后续种子修改仍先预览、人工复核并另行授权写入，首次授权不覆盖新修改。
- V4.1 首个页面正式采用“人工智能产业 -> 四大目录分组 -> 26 个赛道”的产业/赛道总览；四大分组不能因当前只建设一个试点而被省略。
- 当前已实现独立的产业档案阅读端骨架，不是最终视觉定稿。V4 默认入口展示 AI 产业结构，并提供“产业结构、企业档案、人物档案”三个一级选项；赛道发展历程、企业时间线和事件档案仍须在有来源的事件流程中逐步交付。完整方向见 `docs/product/V4_PRODUCT_PAGE_VISION.md`。
- 一个事件应是在相对明确的时间发生、涉及具体参与者、能够被来源支持，并对赛道或参与者发展产生有意义变化的事情。
- 赛道归属和事件类型是两套独立判断：赛道回答“发生在哪里”，事件类型回答“发生了什么”。
- 一个事件可以属于多个赛道；第一版先为事件选择一个主要事件类型。
- AI 处理结果只能形成事件候选，必须经过用户确认后才能成为已确认事件。
- V4.0 的事件粒度、事件类型 v0.1、事件状态和日期精度规则已经确认；规则将在 V4.2 用真实材料检验并允许继续修订。
- 来源身份、获取入口、具体文档、主张、观点和事件必须分开；材料发布者不自动等于文中主张或观点的实际表达者。
- `Claim` 是来自具体文档、可以被证据支持或反驳的可核查陈述；`Viewpoint` 是人物或机构对事实的解释、评价、预测或建议，两者不能复用同一个自由文本对象。
- 主张和观点都必须能够追溯到原始文档与上下文，并允许关联零个、一个或多个事件；AI 提取结果在用户确认前只能作为候选。
- V4.2 首批真实事件就必须支持材料选择、创建或关联事件、人工确认、时间线展示和纠错记录；基本质量机制不延后到 V4.5。
- V4 试用开始记录研究问题和保留材料的理由，以实际研究中的证据回溯、纠错和人工整理成本检验闭环，不提前建设完整 V5、V7 或 V8 引擎。

### 2.2 阶段边界

V4.0 负责制定第一版产业目录、对象关系、事件粒度、类型、状态和日期精度规则。这些规则在缺少试点材料和 AI 处理流程时只能视为初始规则，不能声称已经通过数据验证。

后续验证顺序是：

```text
V4.1：名册导入、阅读端骨架和最小纠错入口已实现
V4.2：首批真实事件跑通材料 → 创建/关联 → 人工确认 → 时间线 → 纠错
V4.3：深化已有事件的多来源文档、主张、观点、冲突和证据
V4.4：完善产业档案阅读，保持逐层追溯和空白、争议展示
V4.5：减少整理、复核和补证据负担，提高新增材料关联效率
```

上述阶段全部以“通用基础模型（含大语言模型）”为内容试点。其他赛道在完整闭环通过前不进入同等深度建设。

候选状态、来源追溯、人工确认、纠错记录和基本完整性检查是 V4.2 第一条可用路径的共同条件。可以先用人工策划和已有材料验证路径，再评估 AI 候选提取的收益；自动采集全部稳定不是开始事件试点的前置条件。

V4 的问题与收藏理由先以最小记录支持试用；V5 分析需保存复查条件，自动触发与持续验证留待后续能力深化。V6—V8 按真实依赖迭代，V9 人物画像为可选分支；V10 跨产业扩展不依赖 V9，但必须先完成当前单赛道闭环和通用能力验证。这些长期规则不扩大本规格的实现范围。

迁移 `0002` 中预置的候选事件类型由迁移 `0003` 升级为已经确认的事件类型 v0.1 规则；迁移 `0004` 将 `segments.segment_kind` 从旧三类升级为已经确认的四类产业目录分组。

### 2.3 待细化事项与写入边界

- 首批名册和阅读端已完成，下一步细化首批事件范围、材料选择与事件编辑流程；尚未确认的事件样本、字段和交互设计仍属草案。
- 首批真实事件需小批量策划与人工审核，不在数据库迁移时自动灌入；名册和来源种子变化继续先预览再授权写入。
- 来源注册表已有调整，但不得由本规格或迁移脚本静默应用到活动数据库；当前待审核内容见 `docs/decisions/V4_2_SOURCE_COVERAGE_REVIEW.md`。
- `python -m orbitai.website_preview` 继续保持只读，不连接 SQLite、不调用 AI、不创建事件候选。正式网页材料管线另行审核；只读试抓的具体门槛见 `docs/specs/V4_2_WEB_SOURCE_PREVIEW_SPEC.md`。

其余假设不会自动成为正式产品结论。用户确认后，再更新本规格。

## 3. V4 的核心工作流

### 3.1 人工策划

1. 用户选择已确认的试点赛道和名册参与者；本轮不扩大内容范围。
2. 用户选择已有文章，或人工补充可追溯材料，并记录研究问题或保留理由。
3. 用户创建候选事件或选择已有事件关联材料，填写或核对日期精度、参与者和关联赛道。
4. 用户为事件关联一个或多个来源文档，并区分官方、独立报道、专家观点、用户反馈或背景材料。
5. 用户检查材料后确认事件，或标记为有争议、待补证据、已归档。
6. 已确认事件进入相关时间线，并能打开事件及原始材料；未确认内容显示真实状态。
7. 用户发现错误后修正、合并或调整状态，保留修改记录；新的材料可继续补入该事件。

### 3.2 文章接入

1. 现有 RSS 文章继续进入 `articles`。
2. 值得进入产业档案的文章显式映射为 `documents`，并保留 `article_id`。
3. 文档可以关联已有事件，也可以在 V4.2 的 AI 流程中产生事件候选。
4. AI 先根据事件粒度提取事件核心，并尝试判断它是否与已有事件为同一件事。
5. AI 分别判断事件的多个赛道归属、一个主要事件类型，以及日期和日期精度。
6. AI 产生的事件默认为 `candidate`；没有用户确认标记时，不允许直接成为 `confirmed`。

2026-09-16 已在最小切片上补齐按需 AI 候选提取、网页与人工材料接入、专门合并和赛道内时间线。活动库首批三条事件仍未确认，2026-09-26 用户功能验收通过；逐条内容确认仍独立进行。AI 仅提议、原文保留、人工确认与来源写入边界继续有效。

### 3.3 浏览追溯

用户应能从产业和赛道逐层进入参与者、事件和文档。一个事件允许关联多个赛道、企业、机构、人物和文档，不能把文章本身当作事件。

### 3.4 最终页面方向与试点期边界

最终面向用户的 V4 页面采用以下浏览路径：

```text
AI 产业结构（默认入口）
-> 赛道介绍与赛道发展历程
-> 各企业发展时间线
-> 时间线上的关键事件
-> 事件档案与原始材料
```

V4 首页上方使用“产业结构、企业档案、人物档案”三个一级选项。“产业结构”默认直接显示 AI 产业的四大分组和 26 个赛道，整体形态应更接近产业结构图，而不是信息流或普通卡片列表。四大分组之间的支持、依赖等关系以后再随产业分析能力加入，本阶段不提前制作。

点击“通用基础模型（含大语言模型）”后进入独立赛道页。页面上部解释赛道边界并展示大致发展历程；发展历程可以从各企业模型发展时间线中归纳共性，但归纳结果必须保留来源、时间范围和不确定性，不能把 AI 总结直接写成无来源事实。页面下部按企业展示发展时间线；V4.2 及以后形成的已确认事件挂到相应时间线上，并可继续进入事件档案。

企业档案和人物档案由首页一级选项直接进入，具体列表、检索和详情布局在相应页面开始开发前再细化。其他顶层产业属于远期范围，当前不为多产业切换提前增加复杂入口。

当前 `/industries/artificial-intelligence` 已使用独立阅读端骨架。先在现有入口上交付通用基础模型的事件、证据和档案闭环；试点完成后，再统一重设计面向用户的 Jinja2 模板和 CSS，不用无来源内容填充尚未实现的时间线。

## 5. 数据模型

### 5.1 产业与赛道

- `industries`：顶层产业边界。
- `segments`：第一版细分赛道；`segment_kind` 只表示赛道所在的四大目录分组。
- `industry_segments`：产业与赛道的多对多关系，避免把全部结构锁成单一树。
- `segment_relation_types`：支持、依赖、供应、采用、竞争、替代、合作、监管和影响。
- `segment_relations`：赛道间的受控关系。

第一版目录正式采用以下四个分组：

| `segment_kind` | 分组 | 第一版细分赛道 |
|---|---|---|
| `core_capability` | 核心能力 | 通用基础模型；多模态理解与生成；推理与规划；智能体核心能力；世界模型与物理智能 |
| `infrastructure` | 基础设施 | 数据；AI 芯片；先进制程、封装和半导体设备；云计算和算力平台；网络和数据中心；电力、能源和冷却 |
| `product_application` | 产品与应用 | AI Agent 与软件自动化；AI 编程和生产力工具；AI 搜索、助手和内容产品；AI 终端和智能硬件；具身智能与机器人；自动驾驶；医疗、教育、金融、制造等行业应用；科学 AI |
| `external_environment` | 外部环境 | 政策与监管；安全治理和标准；资本和融资；人才；开源社区；客户、开发者和用户采用；国际贸易与供应限制 |

四大分组是第一版浏览与归类入口，不代表四棵互不相干的树。一个事件和参与者仍可关联多个赛道，赛道之间继续通过受控关系表达支持、依赖、供应、采用、竞争、替代、合作、监管和影响。

赛道关系使用普通 SQLite 关联表，不引入图数据库。

### 5.2 参与者

- `organizations` 与 `organization_aliases`：企业、实验室、政府部门、社区等组织及别名。
- `people` 与 `person_aliases`：人物及别名。
- `person_organization_roles`：带起止时间的任职或身份关系。
- `organization_segments`、`person_segments`：参与者与赛道的关系。

组织和人物分表保存，避免一个模糊的实体表吞掉各自特有约束。

### 5.3 事件

- `event_types`：第一版事件类型词表。
- `events`：事件的客观内核、状态、时间范围、日期精度、创建来源和人工确认标记。
- `event_segments`：事件可以关联多个赛道。
- `event_organizations`、`event_people`：事件可以关联多个参与者及其角色。

#### 5.3.1 事件粒度

一个事件，是在相对明确的时间发生、涉及具体参与者、能够被一个或多个来源支持，并对赛道或参与者发展产生有意义变化的事情。

- 多篇材料报道同一件事情时，应关联同一个事件，而不是生成重复事件。
- 一篇材料包含多个能够独立命名、独立发生或分别进入时间线的重要动作时，应拆成多个事件候选。
- 普通参数调整、无关紧要的小修复和没有具体发生点的一般评论，不单独形成事件。

#### 5.3.2 事件类型 v0.1

事件类型回答“发生了什么”，赛道归属回答“发生在哪里”。一个事件可以属于多个赛道，但第一版先选择一个主要事件类型。

| ID | 显示名称 | 选择规则与边界 |
|---|---|---|
| `model_release` | 模型发布与重大更新 | 以命名模型首次发布、开放使用或重大版本升级为核心；不含仅使用既有模型的产品功能和仅发表论文的研究结果。 |
| `product_release` | 产品发布与重大更新 | 以面向用户或开发者的 AI 产品、服务、工具或重大功能正式上线为核心；不含底层模型本身发布。 |
| `research_result` | 研究成果发布 | 以新研究方法、实验、评测或科学发现正式公开为核心；若公开可用模型是主体则优先选择模型发布与重大更新。 |
| `corporate_action` | 组织结构变动 | 以组织成立、合并收购、拆分、重组、更名或关闭等结构性变化为核心；不含融资、合作和关键人物任免。 |
| `partnership` | 合作 | 以两个或更多组织正式建立联合开发、授权、供应、分销或战略合作为核心；单方实际使用归为采用与落地。 |
| `funding` | 融资 | 以企业、机构或项目获得股权、债务、战略投资、资助或上市融资为核心；不含收购和无实际交易的估值传闻。 |
| `infrastructure` | 基础设施建设与扩容 | 以算力集群、数据中心、网络、电力或冷却设施建设、投运或显著扩容为核心；不含仅发布硬件产品或仅签署合作。 |
| `policy_regulation` | 政策与监管 | 以政府、监管机构、法院或标准组织提出、通过、执行、调查、处罚或发布正式规则和标准为核心。 |
| `leadership_change` | 管理层变动 | 以对组织或赛道有显著影响的关键人物任命、离职、解职或职务变化为核心；不含普通人员变动。 |
| `adoption` | 采用与落地 | 以明确客户、组织或行业实际选择、部署、集成或扩大使用模型或 AI 产品为核心；不含仅宣布可用或仅表达使用意向。 |
| `incident` | 事故与重大争议 | 以可追溯的服务中断、安全隐私失效、严重滥用、造假撤回或有具体触发点的重大争议为核心；不含一般批评。 |
| `other` | 其他 | 仅用于符合事件粒度但无法归入其他类型的事件；必须说明原因并建议是否新增类型。 |

类型冲突处理规则：

- 模型和产品同时发布时，模型本身是核心则选 `model_release`，用户功能是核心则选 `product_release`；两者都足够重要时拆成两个候选事件。
- 正式建立共同关系选 `partnership`，已经实际部署使用选 `adoption`；签约和上线发生在不同时间时拆成两个事件。
- 只有论文和实验选 `research_result`，公开可用模型是核心则选 `model_release`。
- 问题本身选 `incident`，监管机构的调查、处罚或规则行动另选 `policy_regulation`。
- AI 模型输出主要类型时，还应给出选择理由、是否需要拆分事件和可能的备选类型；业务规则不绑定单一模型。

#### 5.3.3 事件状态

- `candidate`：候选，尚未确认。
- `confirmed`：用户已经检查事件核心，并确认至少有一个可追溯来源支持其基本发生。
- `disputed`：来源对事件是否发生、事件边界、日期或关键陈述存在实质冲突；保留冲突而不是强行统一。
- `needs_evidence`：事件值得保留，但现有材料不足以确认，等待补充可追溯来源。
- `archived`：事件被合并、撤回、判定重复或移出当前范围，不再进入主要浏览路径。

AI 生成的事件默认为 `candidate`，不能在没有用户确认标记时直接成为 `confirmed`。

#### 5.3.4 日期精度

- `day`：可靠信息能够精确到具体日期。
- `month`：只能可靠确定到某年某月。
- `quarter`：只能可靠确定到某年某季度。
- `year`：只能可靠确定到年份。
- `range`：事件本身持续一段时间，应同时保存开始和结束范围。
- `unknown`：当前材料无法可靠确定发生时间。

不得为了排序而虚构更精确的日期；后续材料提高或降低日期确定性时，可以修正日期和精度。

### 5.4 来源与文档

- `sources`：长期追踪的来源身份，可以映射组织或人物。
- `source_entries`：RSS、官网、API、YouTube、播客或手动录入等获取入口。
- `documents`：公告、文章、访谈、报告等原始材料；可通过 `article_id` 映射现有文章库。
- `event_documents`：事件与多个文档的关系，并标记证据角色。

来源身份、获取入口、具体文档和事件必须分开。第一方材料可以证明“谁宣布了什么”，但不能自动证明长期影响或竞争优势。

### 5.5 已确认的主张与观点规则

V4.0 正式确认以下对象边界和关系：

```text
Document -> Claim
Document + Person/Organization -> Viewpoint
Event <-> Claim/Viewpoint
Claim/Viewpoint -> EvidenceLink -> Document fragment
```

- `Claim` 是文档中能够被证据支持、反驳或标记为证据不足的原子化陈述。它必须关联原始文档和对应上下文；如果文中明确给出主张者，还应单独关联实际提出主张的人物或机构。
- `Viewpoint` 是人物或机构对事实的解释、评价、预测或建议。它必须同时关联原始文档和实际表达观点的人物或机构。
- 文档的发布来源与文中主张者、观点表达者是两种身份。例如媒体发布的访谈属于媒体来源，但观点仍归属于受访者。
- 事件与主张、观点都是多对多关系：一个事件可以包含多条主张和观点；同一条主张或观点也可能解释或比较多个事件。暂时无法归入具体事件的主张和观点可以先只保留文档关系。
- 事实主张、人物观点、AI 推断和用户判断必须有不同类型与来源标记，不能复用一个自由文本字段。
- AI 可以提取主张和观点候选，但在用户确认前不能把归属、含义或可信度写成已确认结论。

以上是已经确认的产品规则，但不表示相关物理表已全部实现。`Claim`、`Viewpoint`、它们与事件的关联表、证据片段和用户反馈的物理表仍在事件—文档闭环稳定后通过后续迁移实现；具体字段、状态和证据角色在 V4.3 实现前另行细化。已存在的事件、文档及其基础关联表继续复用。

## 6. 迁移规则

- 所有后续数据库结构变更必须新增版本迁移，不再直接扩写 `init_db()` 中的临时 `ALTER TABLE`。
- 迁移按版本顺序执行，并记录到 `schema_migrations`。
- 每条迁移在事务中执行，失败时不记录为已应用。
- 会删除数据的回滚必须显式传入 `--allow-destructive`。
- `0001` 是兼容现有 V3 文章库的基线，不提供自动删除文章表的回滚。
- 应用迁移前应备份有价值的本地数据库；迁移代码本身不自动复制用户数据库。

命令：

```powershell
python -m orbitai.migrations status
python -m orbitai.migrations up
python -m orbitai.migrations down --allow-destructive
```

正常应用调用 `init_db()` 时也会自动执行尚未应用的迁移。

## 7. 验收标准

### 7.1 V4.0 基线验收

- 新数据库可以一次创建 V3 文章表和 V4 首批核心表。
- 重复初始化不会重复执行或破坏数据。
- V3 早期数据库在迁移后仍保留原文章，并补齐兼容字段。
- 数据库能表达“产业—赛道—组织—事件—来源文档”的完整关联。
- 一个事件能关联多个参与者、赛道和文档。
- AI 来源事件在没有用户确认时不能写成已确认状态。
- 已确认的事件类型 v0.1 名称和选择规则能够从 `event_types` 读取。
- `segments.segment_kind` 只接受核心能力、基础设施、产品与应用和外部环境四个已确认分组。
- 外键约束默认启用。
- 破坏性回滚没有显式许可时会被拒绝。
- Python 编译检查和聚焦测试全部通过。

### 7.2 V4.2 首批事件与 V4 试用验收

以下验收方向已于 2026-09-13 确认，具体样本、记录方式和实现细节在 V4.2 规格中细化：

2026-09-15 按用户反馈明确分工：本节检查的是信息整理、阅读与来源追溯，不要求完成 V5 的因果或影响分析。代理完成工程验证、准备具体成果并整理使用记录；用户承担必要的内容确认与自然的阅读反馈，不逐项执行技术测试或填写验收报告。完整 V4 的后续复用与成本观察不作为每个切片反复暂停的理由，未取得的真实反馈仍须标明未验证。

- 围绕实际研究问题，完成材料选择或人工补充、事件创建或关联、确认、时间线展示和纠错，保留问题与材料收藏理由。
- 每个已确认事件至少有一个可追溯来源；用户能从展示中的事件找回原始材料与支持其基本发生的依据，不能仅返回 AI 摘要。
- 能把新材料补入已有事件；发生重复、日期错误或证据不足时，可以修正、合并或调整状态并保留记录。
- 来源、候选、人工确认和纠错的约束及失败路径有聚焦验证，不等 V4.5 才检查。
- 记录整理、确认、纠错和补证据的时间及人工操作，并与原有浏览、笔记或对话方式比较；AI 候选提取也以需要人工核对和修正的实际成本验收。
- V4 持续试用中验证过去材料和事件能否被重新找到、引用或修正；保留实际案例。收益不足时先改进流程，不以抓取量或页面数量替代使用结果。

V4.3—V4.5 继续满足上述基础条件，并达到路线图中证据区分、多源关联、未知与争议展示等退出标准。当前不预设未经试用验证的节省比例，也不把一次技术通过当作长期使用收益已经成立。

## 8. 首批事件切片的开发顺序（历史参考）

V4.1 名册、阅读端骨架和最小纠错入口已经实现。下一步在已有 `events`、`documents` 及关联表上细化事件仓储、管理流程和时间线，不重复建设已完成目录。

1. 策划第一批真实事件、时间范围和材料；明确选择与拆分依据，继续限定既有 6 个组织和 6 位人物。
2. 编写 V4.2 实现规格，核对现有表与完整整理流程之间的缺口，明确必要的迁移、确认和纠错规则。
3. 先用人工选取材料验证第 3.1 节的完整路径；涉及真实事件种子的导入先经本轮人工审核，名册和来源种子继续遵守原有预览与授权流程。
4. 在事件可用后深化多源证据与阅读，并评估 AI 提取能否减少总整理成本；不要求先补齐所有自动来源。
5. 按第 7.2 节开展真实试用，记录问题、复用和人工负担，再决定后续效率改进。

路线调整本身不授权执行迁移、导入名册或来源种子，也不授权把官网只读命令接入数据库和 AI 队列。
