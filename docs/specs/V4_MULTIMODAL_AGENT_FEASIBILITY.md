# 多模态材料与外部代理可行性评估

类别：实现前可行性评估

状态：草案，待用户阅读与试验；2026-09-13 用户提出用 Grok Bot 降低材料收集和分析负担。本文件记录官方公开资料核查及建议方案，未确认选型、试验预算或正式接入，也未执行 Bot 任务。

日期：2026-09-13。产品能力与套餐信息可能变化，试用前复核相关官方页面。

## 1. 要验证的问题

OrbitAI 当前只有部分文章自动入口。图像、视频的困难包含三个不同步骤：找到并取得可用材料、提取其中的信息、将信息关联到事件和证据。需要分别测量，不能用一份流畅摘要代表三个步骤都成功。

本评估的假设是：Grok Bot 可作为可替换的外部材料助手，减少跨网站操作、文件整理、初步提取和候选分析成本。实际收益尚未在 OrbitAI 材料上验证；它不作为 V4.2 最小事件闭环的前置依赖。

## 2. 官方资料能确认到哪一步

| 能力 | 已核实信息与来源 | 对 OrbitAI 的含义 |
| --- | --- | --- |
| 持续工作环境 | 云电脑具有浏览器、文件系统、终端，支持连接器；云电脑与用户本机分离。[电脑与应用](https://docs.x.ai/grok-bot/computer-and-apps) | 可以试验跨网页查找与文件交付，不能假设它已连接本地 OrbitAI |
| 多模态输入 | Bot 本身接受图像、音频和视频附件；桌面一次最多 6 个附件，文档/图像/音频每个最高 25 MB，视频最高 200 MB。[文件与结果](https://docs.x.ai/grok-bot/files-and-results) | 可以测试上传材料；不等于已证明长视频完整理解、OCR 或转写准确 |
| 可审阅成果 | 官方说明可返回文档、表格、截图和日志等成果，并保存文件。[文件交付](https://docs.x.ai/grok-bot/files-and-results#ask-for-a-reviewable-result) | 先测试稳定的文件交接，不假设存在无人干预的本地导入协议 |
| 可重复工作 | 支持保存 skill，并用 routine 定时或在支持的事件发生时执行；官方建议先验证单次流程。[Skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations) | 单次试验可靠后才考虑持续收集，首轮不安排全天运行 |
| 访问与使用量 | 当前计费页列出付费 Cursor 个人计划、Teams，以及可关联的个人 SuperGrok 系列或 X Premium+；有每周用量和可选超额计费。[套餐与计费](https://cursor.com/help/grok-bot/plans) | 本次没有核查用户账户权益，不据此要求购买；试用记录产品用量和费用 |

官方页面并未为本研究任务证明以下效果：通用网站视频可完整读取、说话者和时间码准确、图表数字及脚注无遗漏、中文或细小文字 OCR 可靠。公开材料中的 Grok API 能力也不能自动视为 Grok Bot 的内置能力或订阅额度。

本次未找到可据以设计 OrbitAI 集成的 Bot 公共任务 API、webhook 或自动取回结果协议；这表示尚未核实，不表示断言这些接口不存在。初期按人工保存成果文件设计试验，不承诺全自动接入。

## 3. 建议分工与交付路径（待验证）

```text
已有 RSS / 人工选取的公开材料 / 外部 Bot 收集
    → 带来源与定位的材料包
    → 本地待审材料
    → 校验、去重、人工复核
    → 经另行规格与授权的导入流程
    → OrbitAI 事件、证据及分析草稿
```

Bot 先负责查找、摘录、初步提取、提出事件关联与分析候选。OrbitAI 保留材料身份、证据关系、确认状态和修改历史；人工审核继续决定是否确认。外部助手产生的摘要、OCR、转写或分析都是派生结果，不能冒充原始材料。

云端首轮仅使用选定的公开或用户有权提供的材料，结果以文件交回。不给 Bot 整个项目目录、活动数据库或 `.env`，不开放本地服务来追求即时同步。当前 `website_preview` 保持只读，新的材料导入必须独立设计。

对于网页，优先保留可核查的正文和原始链接；对于图像和视频，分别检验“取得材料”与“提取信息”，避免把后者能力当成前者成功。

| 材料 | 试验中要求的提取结果 | 保留的证据定位 |
| --- | --- | --- |
| 网页/文章 | 原文摘录、标题、日期及候选事件；获取失败单列 | 原始 URL、获取时间、原文段落与材料版本 |
| 图像/图表 | 图中文字和可见数据，单位、坐标、图例与不清晰处 | 原始来源、图像文件或可访问引用、页码/区域；OCR 与视觉解释分开 |
| 音视频 | 字幕或转写片段、实际表达者、候选主张；视觉信息单独记录 | 原始视频链接、起止时间码；字幕/ASR/画面提取来源与片段版本 |

有字幕的视频先评估字幕是否足够回答问题；重要图表或演示仍需检查对应画面。没有现成字幕时，若能取得可处理的音视频，可测试转写与画面提取；既没有可用字幕、也无法取得可处理媒体时，记为待补材料，不用标题、简介或模型推测填补。视频中的发言归属不自动等于频道发布者。

## 4. 首轮小样本对照方案（建议，尚未运行）

范围保持在通用基础模型及现有试点名册内，建议一个 Bot、约 8 个固定样本：2 篇网页、2 份含图表的材料、2 段有字幕视频、2 段无现成字幕的短视频。附件分批处理；样本数量是试验建议，不是新的 V4 退出门槛。

1. 先定一个真实研究问题，选出相关材料；记录人工处理所需步骤和时间，保留一份可核对的摘录。
2. 用相同材料和输出要求完成一次 Bot 任务；其中视频同时测试网址入口和附件入口，分别记录失败，不能把人工下载上传的时间省略。
3. 对照原文、图像或视频，检查引用、数字、说话者、时间码与遗漏。清楚记录 Bot 实际读到哪一部分，不以接受附件代表覆盖整份材料。
4. 保存 JSON/CSV 清单与证据文件到独立待审目录；先人工检查格式，不对活动库运行导入。
5. 比较全部人工耗时与质量，决定保留哪些步骤、是否改用专门的转写/OCR组件，或暂时维持人工。

每次交付的最小内容为：来源 URL、发布者与实际表达者、日期及精度、媒体类型、获取时间、材料或片段版本、摘录与定位、提取方式（原文/字幕/OCR/ASR/视觉解释）、候选事件或主张、未验证项与失败原因。处理者及已知模型信息可记录；产品不暴露的底层模型版本标为未知。

这是一份交付要求，尚非已实现的导入格式。先让输出可稳定审核，再决定是否编写适配器；不提前锁定 Grok Bot 为唯一供应商。

## 5. 继续投入的判据

- 获取：多少材料真正读到正文或目标媒体片段，多少需要登录、人工接管或上传补充。
- 证据：链接、数字、单位、说话者与时间码能否回到原材料；有没有虚构、漏读或把官方说法写成已证实效果。
- 分析：候选描述是否准确区分事实与推断，能否正确关联已有事件；更长的摘要不单独计为收益。
- 人工成本：总时间包含找材料、提示、上传、接管、复核、修正及整理文件；与人工基线比较，不能只计算 Bot 运行时间。
- 运行成本：记录可见用量、费用、重试和失败。试验前明确可接受预算及终止条件，不把订阅访问权理解为无限使用量。

若证据质量可接受且净人工时间减少，再讨论扩大样本、保存 skill、增加 routine 或单独 API 组件。若获取省时但转写不可靠，可只保留收集功能；若复核成本抵消收益，则不进入正式材料流程。具体阈值和样本由试验安排确定，本文件不宣称已通过评测。
