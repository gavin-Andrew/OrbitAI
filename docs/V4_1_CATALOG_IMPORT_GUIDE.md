## 2. 整体逻辑关系

```text
名册种子 JSON + 旧来源注册表
            |
            v
      结构与业务校验
            |
            v
   与当前 SQLite 数据逐条比较
            |
            v
      生成只读导入预览
            |
       用户明确确认
            |
            v
 BEGIN IMMEDIATE 开启写事务
            |
            v
  只插入缺失且无冲突的记录
            |
            v
 外键检查 -> 提交；任一步失败 -> 整批回滚
```

这个顺序的核心思想是：先判断，再写入。数据库不是用来试错的第一站，预览报告才是。

## 3. 为什么分成仓储层和导入层

### 3.1 仓储层

仓储层负责回答“数据怎样进入 SQLite”：

- 哪些种子字段对应哪些表字段。
- 产业、赛道、参与者、任职、来源应该按什么外键顺序写入。
- 记录已经存在时是跳过、拒绝还是插入。

它不负责决定某个草案事实是否已经核实。这样可以避免把业务审批规则散落进 SQL。

仓储层采用“只增不改”策略：

- 稳定键不存在：插入。
- 稳定键存在且内容相同：跳过。
- 稳定键存在但内容不同：抛出冲突，不覆盖。

因此，即使未来其他代码绕过命令行直接调用仓储层，用户修改仍有第二道保护。

### 3.2 导入层

导入层负责回答“这份输入现在能不能写”：

- JSON 结构是否完整。
- 四大分组与 26 个赛道的数量是否吻合。
- 6 个组织、6 位人物和 13 个来源是否满足确认范围。
- 组织、人物、赛道、任职、来源之间的引用是否闭合。
- Google DeepMind / Google AI 拆分是否与旧注册表一致。
- 当前数据库是否已有相同身份或不同内容。

只有校验无错误且预览无阻断项时，报告中的 `can_apply` 才会是 `true`。

## 4. 必要技术背景

### 4.1 稳定 ID、主键和外键

主键用于唯一识别一条记录。例如组织的 `openai` 和人物的 `sam_altman` 都是稳定 ID。显示名称以后可以修改，但稳定 ID 不随标题变化。

外键用于保证关系两端真实存在。例如 `person_segments` 中的人物 ID 和赛道 ID 必须分别存在于 `people` 和 `segments`。写入完成后还会运行 `PRAGMA foreign_key_check`，确认没有悬空关系。

### 4.2 名称规范化

身份比较使用：

- Unicode NFKC 规范化。
- 去除首尾空格。
- 折叠连续空格。
- 英文大小写折叠。

例如全角的 `ＯｐｅｎＡＩ`、`OPENAI` 和两侧带空格的 ` OpenAI ` 会得到同一个检索键。这样可以发现潜在重复身份。

规范化只用于比较，数据库和页面仍保存用户认可的原始显示名称。

### 4.3 导入预览（dry run）

预览只读取数据库，不创建表、不写业务数据。它把每条计划分为：

| 动作 | 含义 | 是否阻断 |
|---|---|---|
| `create` | 数据库缺少该记录，确认后可创建 | 否 |
| `map_existing` | 复用旧来源注册表身份并写入 V4 表 | 否 |
| `create_from_split` | 根据已确认拆分创建来源 | 否 |
| `intentionally_unbound` | 创建有意暂不绑定参与者的补充来源 | 否 |
| `unchanged` | 数据库与种子相同，重复执行会跳过 | 否 |
| `update_preview` | 同一稳定键的内容不同，只展示差异 | 是 |
| `conflict` | 名称、别名、slug 或入口唯一键碰撞 | 是 |

`update_preview` 被设计成阻断项，是为了落实“不静默覆盖用户修改”。后续人工纠错流程可以让用户明确选择保留数据库内容或采用新内容。

### 4.4 事务与回滚

事务可以把多条 SQL 当作一次完整操作。本实现使用 `BEGIN IMMEDIATE`：

- 开始时取得 SQLite 写锁，减少预览后数据被另一写入者改变的窗口。
- 所有记录成功并通过外键检查后才 `COMMIT`。
- 任意一条 SQL 失败就 `ROLLBACK`，先前插入的产业、赛道或组织也全部撤销。

这保证数据库不会停留在“产业已经写入，但参与者只写了一半”的状态。

### 4.5 幂等

幂等表示重复执行不会不断制造新数据：

```text
执行一次后的状态 == 执行两次后的状态
```

首次写入时缺失记录会创建；第二次预览会把它们全部判断为 `unchanged`，写入数量为 0。主键和组合主键提供数据库约束，仓储层再执行内容一致性检查。

### 4.6 索引

索引不改变数据本身，而是保存便于查找的数据结构。`0005` 为以下路径建立索引：

- 产业、赛道、组织和人物名称。
- 组织与人物别名。
- 从赛道反查组织或人物。
- 从组织反查任职人物。
- 从组织或人物反查来源。

索引会增加少量磁盘占用和写入成本，但名册读取远多于修改，适合当前研究系统。

## 5. 怎样运行

### 5.1 只读预览

```powershell
python -m orbitai.catalog_import preview --summary-only
```

去掉 `--summary-only` 可以查看全部逐条操作和差异：

```powershell
python -m orbitai.catalog_import preview
```

预览不会替你初始化一个不存在的数据库，因为“只读”不应暗中产生新文件或迁移。

### 5.2 显式写入

只有完整预览经过人工检查后才运行：

```powershell
python -m orbitai.catalog_import apply `
  --confirm-seed-id v4_1_foundation_models_roster `
  --summary-only
```

`--confirm-seed-id` 必须与 JSON 中的 `seed_id` 完全相同，用于降低误把另一份种子写入当前数据库的风险。`apply` 会先应用尚未执行的数据库迁移，再重新校验和预览，不能依靠旧预览绕过当前冲突。

这些警告会继续出现在预览中，不会因为记录进入数据库就变成“已完全核实”。核查状态和核查来源当前属于导入元数据；现有 V4.0 业务表没有对应字段，因此不会被强塞进错误的数据列。

## 7. 自动测试覆盖什么

- 正常种子能够通过校验。
- 错误引用和规范化后的名称碰撞会被拦截。
- 预览前后各业务表行数完全相同。
- 首次写入得到预期行数。
- 第二次写入新增 0 行。
- 用户修改已有描述后，预览显示差异且写入被阻止。
- 人为制造中途数据库失败时，整套名册回滚为 0 行。
- `0005` 查询索引能够随迁移创建。

测试全部使用临时数据库，不会污染正式 `var/orbitai.db`。
